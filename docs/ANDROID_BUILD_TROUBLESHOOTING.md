# Android Build Troubleshooting

## `jlink executable ... does not exist` (androidJdkImage transform failure)

### Symptom

```
> Task :react-native-community_blur:compileDebugJavaWithJavac FAILED

Could not resolve all files for configuration ':react-native-community_blur:androidJdkImage'.
   > Failed to transform core-for-system-modules.jar to match attributes {artifactType=_internal_android_jdk_image, ...}.
      > Execution failed for JdkImageTransform: ...\platforms\android-36\core-for-system-modules.jar.
         > jlink executable C:\Users\<you>\.antigravity-ide\extensions\redhat.java-1.55.0-win32-x64\jre\...\bin\jlink.exe does not exist.
```

Can show up on `npx react-native run-android`, `gradlew assembleDebug`, or any module built against `compileSdkVersion` 30+.

### Root cause

AGP builds a stripped-down JDK image (`androidJdkImage` transform) from `core-for-system-modules.jar` for API 30+, and that transform needs `jlink`, which only exists in a **full JDK** — not a JRE.

Some IDEs/editor extensions (here, the RedHat Java Language Support extension bundled with an IDE at `~/.antigravity-ide/extensions/redhat.java-*`) ship their own minimal **JRE-only** runtime just to run their language server. If Gradle's toolchain/daemon resolution picks that JRE instead of a real JDK (Android Studio's bundled `jbr`, Adoptium, etc.), `jlink.exe` won't exist there and the transform fails — even though `JAVA_HOME` looks correct.

There are two independent places Gradle picks a JVM from, and **both** need to point at a real JDK:

1. **Toolchain resolution for compilation** — controlled by `org.gradle.java.home` / `org.gradle.java.installations.*` in `android/gradle.properties`.
2. **The JVM the Gradle daemon itself runs on** — controlled by `android/gradle/gradle-daemon-jvm.properties` (Gradle 8.8+ "daemon JVM criteria" feature, generated by `gradlew updateDaemonJvm`). This can silently auto-detect/auto-provision a JVM that satisfies its `toolchainVersion`, independently of `org.gradle.java.home`.

A **stale Gradle daemon** that started before you fixed either of those files will keep using the old (bad) JVM until it's stopped — the properties files are only read when a new daemon spins up.

### Fix

1. Pin the JDK explicitly in `android/gradle.properties` (already present in this repo):

   ```properties
   org.gradle.java.home=C:/Program Files/Android/Android Studio/jbr
   org.gradle.java.installations.auto-detect=false
   org.gradle.java.installations.paths=C:/Program Files/Android/Android Studio/jbr
   ```

   Use any full JDK you have installed (Android Studio's bundled `jbr` is the easiest — it's always a complete JDK with `jlink.exe`).

2. Check `android/gradle/gradle-daemon-jvm.properties` — its `toolchainVersion` must match a JDK that's actually discoverable (i.e. one of the paths from step 1, or otherwise auto-provisionable). If unsure, delete the file to fall back to legacy `org.gradle.java.home`-based daemon selection, or regenerate it with:

   ```powershell
   cd android
   .\gradlew.bat updateDaemonJvm --jvm-version=21
   ```

3. **Kill any running Gradle daemon** so the new settings actually take effect:

   ```powershell
   cd android
   .\gradlew.bat --stop
   ```

4. Re-run the build:

   ```powershell
   npx react-native run-android
   ```

### Quick verification

```powershell
Test-Path "C:\Program Files\Android\Android Studio\jbr\bin\jlink.exe"   # should be True
```

If you ever see this error again after editing `gradle.properties`, the fix almost never "didn't work" — you just forgot step 3 (`gradlew --stop`) and a stale daemon is still holding the old JVM.

### Related settings

- `JAVA_HOME` (system env var) should also point at a full JDK, but it is **not** sufficient on its own if `gradle-daemon-jvm.properties` exists and resolves to something else.
- If you switch machines/JDK install paths, update `org.gradle.java.home` and `org.gradle.java.installations.paths` in `android/gradle.properties` to match.
