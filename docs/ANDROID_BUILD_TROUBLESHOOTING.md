# Android Build Troubleshooting

This file used to document a machine-specific workaround for the JDK issue
below. That workaround has since been replaced with a portable, project-level
fix (see "Current state" in each section) — if you're troubleshooting a fresh
symptom, read that first; the "Historical symptom" sections exist so the old
error messages are still searchable.

## `jlink executable ... does not exist` (androidJdkImage transform failure)

### Current state (fixed at the project level)

`android/gradle/gradle-daemon-jvm.properties` is committed to the repo and
pins the Gradle daemon's required JVM to **version 21, vendor Microsoft**.
`android/settings.gradle` applies the
`org.gradle.toolchains.foojay-resolver-convention` plugin, so if your machine
doesn't already have a matching JDK, Gradle downloads one automatically —
no manual JDK install or path configuration needed on any machine or CI
runner. Do **not** add `org.gradle.java.home` (or any other absolute path) to
the tracked `android/gradle.properties` — it's machine-specific and would
silently break the build for everyone else. A local override, if you ever
need one, belongs in your own `~/.gradle/gradle.properties`, never in the repo.

### Historical symptom

```
> Task :react-native-community_blur:compileDebugJavaWithJavac FAILED

Could not resolve all files for configuration ':react-native-community_blur:androidJdkImage'.
   > Failed to transform core-for-system-modules.jar to match attributes {artifactType=_internal_android_jdk_image, ...}.
      > Execution failed for JdkImageTransform: ...\platforms\android-36\core-for-system-modules.jar.
         > jlink executable C:\Users\<you>\...\extensions\redhat.java-*\jre\...\bin\jlink.exe does not exist.
```

### Root cause

AGP builds a stripped-down JDK image (`androidJdkImage` transform) from
`core-for-system-modules.jar` for API 30+, and that transform needs `jlink`,
which only exists in a **full JDK** — not a JRE. Some editor extensions (here,
the RedHat Java Language Support extension) ship their own minimal **JRE-only**
runtime for their language server. Gradle's own "daemon JVM criteria" feature
(`gradle-daemon-jvm.properties`) auto-detects *any* installed JDK matching its
`toolchainVersion` — with no vendor pinned, it can match that JRE just as
happily as a real JDK, since version alone isn't a strong enough constraint.
Pinning `toolchainVendor=MICROSOFT` (or whichever real JDK you use) rules out
a vendor-less trimmed JRE like that one, since it reports no vendor at all.

If you ever see this again: check that `gradle-daemon-jvm.properties` still
has both `toolchainVersion` and `toolchainVendor` set, and that a stale daemon
isn't holding an old JVM — `cd android && ./gradlew --stop` before retrying.

## `./gradlew clean` fails inside a native module's CMake clean task

### Symptom

Different modules, same shape of error, always inside an
`externalNativeBuildClean*` task:

```
> Task :react-native-reanimated:externalNativeBuildCleanRelease FAILED
CMake Error in CMakeLists.txt:
  Imported target "react-native-worklets::worklets" includes non-existent path
  ".../node_modules/react-native-worklets/android/build/prefab-headers/worklets"
ninja: error: rebuilding 'build.ninja': subcommand failed
```

or

```
CMake Error: Cannot specify link libraries for target
"react_codegen_RNDateTimePickerCGen" which is not built by this project.
ninja: error: rebuilding 'build.ninja': subcommand failed
```

### Current state (fixed at the project level)

`android/build.gradle` disables every subproject's generated
`externalNativeBuildClean*` tasks and replaces them with a plain recursive
delete of that module's `.cxx`/`build` directories. This is a project-wide
fix, not per-module — it covers any native module hitting this, present or
future.

### Root cause

AGP's `externalNativeBuildClean` task reconfigures CMake (regenerates
`build.ninja`) before it can compute what to delete. When a module's
`CMakeLists.txt` references a target generated by *another* module (a prefab
package, a Codegen target), that reconfigure depends on the other module's
build output still being on disk — but Gradle gives independent modules'
`clean` tasks no defined ordering. If the other module's own `clean` already
deleted its build output first, the reconfigure dangling-references it and
fails. Reproduces on a plain `gradlew clean` from a fresh checkout; not fixed
by changing AGP/Kotlin/Gradle versions.

## `ninja: error: manifest 'build.ninja' still dirty after 100 tries` (release builds only)

### Symptom

Only on `assembleRelease` (never `assembleDebug`), deterministically, every
time — not intermittent, not fixed by `--no-parallel`, not caused by
antivirus timing:

```
C++ build system [build] failed while executing:
    ninja.exe -C .../react-native-reanimated/android/.cxx/RelWithDebInfo/<hash>/armeabi-v7a reanimated
ninja: error: manifest 'build.ninja' still dirty after 100 tries
```

### Current state (fixed at the project level)

`android/build.gradle` redirects `react-native-reanimated`'s CMake staging
directory to `C:/tmp/cxx-modules/react-native-reanimated` on Windows, mirroring
the same workaround `android/app/build.gradle` already applies to `:app`
itself (`buildStagingDirectory` → `C:/tmp/cxx`).

### Root cause

This is a Windows `MAX_PATH` (260 character) problem, not LTO, not a Gradle
parallelism race, and not antivirus — both of those were tested and ruled out
directly. reanimated's native build path is already ~250 characters deep
*before* the object filename:

```
.../node_modules/react-native-reanimated/android/.cxx/RelWithDebInfo/<hash>/armeabi-v7a/
  CMakeFiles/reanimated.dir/<32-char-hash>/interpolation/groups/ArrayPropertiesInterpolator.cpp.o
```

Once ninja's own generated paths cross the Windows path limit, its file
reads/writes/stats become unreliable — which is exactly what "manifest still
dirty" looks like. `:app`'s own CMake project already had this exact
workaround; every autolinked native module building deep inside `node_modules`
needed the same protection but didn't have it. If another autolinked module
hits this same signature, add it by name next to `react-native-reanimated` in
`android/build.gradle` — don't widen the match to every `com.android.library`
subproject blindly, since a module with no `cmake` block at all would break if
`externalNativeBuild.cmake` were configured on it (AGP would expect a real
CMake project to validate).

## `-flto=thin` and other upstream native-module bugs

`react-native-reanimated`'s own `android/CMakeLists.txt` unconditionally
enables `-flto=thin` for release builds. That flag was investigated as a
possible cause of the ninja issue above (ruled out — the failure reproduces
identically with LTO fully removed) but is still worth disabling on Windows,
since thin-LTO's own toolchain support is more fragile there. This is applied
via **patch-package** (`patches/react-native-reanimated+*.patch`, reapplied
automatically by the repo's `postinstall` script on every `npm install`) since
the file lives in `node_modules` and would otherwise be overwritten on every
reinstall. If you need to patch another third-party native module's build
config, follow the same pattern: edit the file directly under `node_modules`,
run `npx patch-package <package-name>`, commit the resulting `patches/*.patch`
file — never hand-edit `node_modules` and expect it to survive a reinstall.

## Release signing

`android/app/build.gradle` looks for release signing credentials in this
order: environment variables (`RELEASE_STORE_FILE`, `RELEASE_STORE_PASSWORD`,
`RELEASE_KEY_ALIAS`, `RELEASE_KEY_PASSWORD` — for CI), then
`android/keystore.properties` (gitignored; copy
`android/keystore.properties.example` and fill in real values for a local
release build). If neither is configured, release builds fall back to the
debug keystore and print a warning during the Gradle build — this keeps
`assembleRelease` working out of the box, but a debug-signed release build
must never be the one you actually ship.
